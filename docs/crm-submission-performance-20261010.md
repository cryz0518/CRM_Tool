## 结论

慢的是完整提交工作流，主要证据指向智能表格访问及队列等待，不能直接归因于 CRM 创建接口。
明确存在智能表格限流、多个 CLI 调用的串行累积和固定动作租约未续期。
审计镜像重复调度及高负载是并发放大因素，但未做停用对照，贡献比例仍无法精确量化。

## 智能表格限流和重复调用

11:25–11:46 的 Worker 日志包含 7 次 `850005`、18 次 CLI 重试日志。
11:27:52–11:28:00 期间四个 ForkPoolWorker 先后触发限流；11:30:55–11:30:59 再次出现。
现场只读表结构查询也复现了 `rate_limited / 850005`，重试后成功。

当前提交路径：

1. `submit_selected()` 读取全表，判断勾选目标当前是否可提交。
2. 对选中线索串行调用 `_submit_create()`。
3. 每条调用 `reconcile_submission()` 再读该记录，执行人工编辑保护。
4. 如发现人工修改，维护审核元数据，再次回读最终快照。
5. 完成必填、枚举与用户映射校验，调用 CRM 查重及创建。
6. 创建成功后回写表格提交状态；适配器执行写前读取、更新和写后真实核验。

正常路径每条线索约涉及 4 次 CLI 记录调用（提交前读取，以及状态回写的读/写/核验）；
人工编辑保护、结构缓存刷新或限流重试会增加调用次数。
多条串行处理，使每次几秒甚至几十秒的智能表格访问持续累积。
提交前读取和写后核验用于保证正确性，不能为了提速直接移除。

## 排队、资源与租约

事发时 2 核服务器系统负载约 9，消息和提交动作共用 Worker 队列。
此前固定一小时窗口至少完成 2,989 次审计镜像消费任务，大量返回 `already_processing`。
审计调度在消费认领前可重复投递同一条待处理记录，增加队列和数据库工作量。
这个观察与 2–4 分钟动作排队同时出现，但没有停用审计对照实验，不能量化其独立影响。

12:08 的额外 CPU 采样约 88% 空闲、steal=0、iowait=0，说明服务器不是持续处于同一高负载状态。
Docker 未为应用/Worker 设置显式 CPU 配额，没有容器重启或 OOM 证据。

动作租约固定为 300 秒；330 秒和 318 秒批次在完成结果时已经失去认领资格。
因此出现“领域操作已开始但 Worker 失联，需要恢复核对”；已有 CRM 成功事实并未被回滚。

## 建议修复顺序

1. 收敛审计镜像的重复投递，避免审计流量挤占录入和提交；共同控制智能表格访问并发与限流退避。
2. 在慢速读表之前检查可确定的 CRM 用户映射缺失，避免必然失败的线索仍串行完成外部读表流程。
3. 减少同一操作内无必要的重复结构/记录获取，保留每条提交前的最新快照及写后核验。
4. 为实际仍在处理的动作续租，并基于逐条持久化结果恢复汇总，不以无限延长超时替代性能修复。

本次没有修复或部署；未重放 CRM 写入，未做压测或停用审计的对照实验。
