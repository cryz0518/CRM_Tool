# CRM 线索自动录入：实施规格（待确认）

> 状态：`frozen`
>
> 依据：`AGENTS.md`、`CONTEXT.md`、ADR-0001 至 ADR-0027。
>
> 本规格只固化已确认的产品和架构决策；外部系统的真实接口尚未提供处列为实施依赖，不作假设。规格已确认并冻结；后续实现仍须遵守“不经明确指令不推送远端、不创建 Pull Request”的约束。

## Problem Statement

销售在企业微信机器人单聊中发送的客户信息具有碎片化、多模态、多轮补充和多客户混杂的特点。系统需要可靠接收这些信息，将其转换为销售可审核的企业微信智能表格记录，并在销售明确授权后按 CRM 的既有规则批量创建或更新 CRM 线索。

首期的关键风险不是“尽可能多填字段”，而是：消息不丢失、不串客户、不越权、不覆盖销售人工修改、不因第三方失败阻塞后续工作，以及不把智能表格与 CRM 的不同归属语义混为一谈。

首期可验收闭环为：授权销售向企业微信智能机器人发送客户信息，后端可靠落库并识别销售，经 AI 提取后创建或增量更新该销售可见的智能表格记录；销售审核后通过确定性机器人命令提交，系统以最终快照调用 CRM Adapter，并返回逐条结果。企业微信机器人、智能表格/wecom-cli 和 Qwen 为首期真实接入；企查查和 CRM 可先以可替换 Mock 实现完成闭环。

## Solution

采用 Python 模块化单体：FastAPI 负责健康检查、内部管理接口和 Operations Console；企业微信 AI 机器人 SDK 的长连接接入层负责收消息；Worker 异步完成媒体处理、AI、企查查、智能表格与 CRM 操作。所有外部系统通过 Adapter/Provider 隔离，业务模块不直接依赖 SDK、HTTP 客户端或 `wecom-cli` 命令。

系统先在同一数据库事务中保存原始消息与 Outbox 事件，再由 Worker 消费。以 `message_id` 去重，同一销售按持久化顺序串行处理，不同销售可并行。任何外部调用失败都不会丢失原始消息；失败任务进入可重试或人工处理状态，而不是错误改变线索业务状态。

企业微信智能表格是销售个人审核工作区，不是全局 CRM 主数据副本。智能表格阶段仅在“当前销售 + 标准公司名称”范围内去重；跨销售同公司记录允许并存且互相不可见。CRM 提交阶段才按公司名称进行全局去重，CRM 的既有规则决定最终创建、更新和 CRM 负责人。

## User Stories

1. 作为授权销售，我向机器人发送有效客户文本时，系统应自动开始采集，不要求我先发送“开始录入”。
2. 作为非授权企业微信成员，我发送消息时，系统不得创建线索、临时线索、智能表格记录或 CRM 任务，也不得调用 AI 提取；可收到一次权限不足提示。
3. 作为销售，我发送名片、截图、语音或文件时，原始消息必须先可靠保存；单个媒体处理失败不得丢失消息或阻塞我后续发送的信息。
4. 作为销售，我连续发送同一客户的碎片信息时，系统必须按消息持久化顺序处理，并将安全的新信息增量补充到正确记录。
5. 作为销售，我和其他销售都记录同一家公司时，我只能看到自己的智能表格记录；系统不得在智能表格阶段把我们的记录合并，也不得泄露对方信息。
6. 作为销售，我再次发送自己已有公司的信息时，系统应优先定位我的既有记录并增量更新，而不是新增重复行。
7. 作为销售，系统 AI 已填写的字段被我在智能表格中改过后，后续 AI 不得静默覆盖该字段。
8. 作为销售，当 AI 对字段只有中等置信度但候选值合法时，我可以先看到预填候选和 `AI待确认` 提示；低置信度候选不应污染正式字段。
9. 作为销售，若待提交线索含有仍未确认的 CRM 必填 AI 候选，系统应在我提交时集中要求我显式确认，而不是在采集过程中反复打断我。
10. 作为销售，若机器人卡片确认能力不可用，我应被引导在智能表格中选择合法必填值，而不是由系统猜测我已确认。
11. 作为销售，我暂时未提供可靠公司名称时，系统应保存可用的联系人、需求和联系方式为临时线索；该记录不可提交 CRM，直到公司名称被可靠识别或我人工补充。
12. 作为销售，临时线索后来识别到公司名称时，系统只能与我自己的同公司记录去重和合并；不得查询、提示或合并其他销售的同公司记录。
13. 作为销售，国内公司企查查无结果、超时或多候选时，我仍可继续审核和采集；我人工确认的公司名称可用于我的表格去重和 CRM 提交，同时系统保留“未唯一工商核验”的事实。
14. 作为销售，明确属于国外的公司不应被强制企查查标准化；英文名称、`.com` 邮箱或国际号码本身不得被当作国外证据。
15. 作为销售，超过当前客户上下文有效期后，我只发送“预算约 20 万”一类弱身份信息时，系统应将其保留为待归属消息，而不是强行附着到历史客户。
16. 作为销售，我可以通过确定性机器人命令或候选卡片将自己的待归属或错误归属消息重新关联到自己有权限的线索；该操作必须被审计且安全重算增量。
17. 作为销售，我发送“提交今天的线索”时，系统只提交我在 Asia/Shanghai 当天首次采集、仍待创建且当前快照尚未成功提交的记录。
18. 作为销售，我发送“提交我的更新”时，系统应主动比较我已同步记录的当前智能表格 CRM 数据与最后成功快照，只提交真实发生 CRM 业务字段变化的记录。
19. 作为销售，我的批量提交中某条缺字段或 CRM 超时时，其他记录仍应独立继续；我应得到成功、待完善和失败数量的汇总。
20. 作为销售，我没有有效 CRM 用户映射时，仍可采集和审核，但提交必须被明确拒绝为不可重试的映射缺失，不得以管理员或公共 CRM 账号代提交。
21. 作为销售，CRM 中已有同公司线索时，我的有效数据可按 CRM 既有规则更新该线索；我只是本次提交销售，不因此成为 CRM 负责人，也不得获知原负责人或其他销售的信息。
22. 作为销售，CRM 成功后系统不得把 CRM 返回的联系人、公司名、负责人等业务字段反向覆盖我的智能表格记录。
23. 作为销售，我只能通过受控的“废弃当前线索”流程废弃自己未同步的线索；不能直接删除智能表格记录，也不能通过模糊自然语言让 AI 猜测废弃目标。
24. 作为销售，废弃操作需要对唯一安全目标二次确认；没有唯一候选、上下文失效或线索已同步时，系统必须要求我选择或拒绝操作。
25. 作为管理员，我能在 Operations Console 查看全部线索、消息、待归属消息、任务、失败、冲突、同步记录和审计，并能执行受审计的重试、提交、归属调整、废弃、创建和转交操作。
26. 作为管理员，我把一条智能表格记录从销售 A 转交给销售 B 时，系统只改变当前 Smart Table Owner，验证 B 获得表格权限且 A 失去权限；不得改变原始采集销售或 CRM 负责人。
27. 作为管理员，我重试一条失败消息时，系统只将其作为受保护的补充处理：使用当前最新线索和人工修改保护，不回放后续消息，也不覆盖后来确认的数据。
28. 作为管理员，我默认只能看到脱敏的手机号、邮箱、原始消息摘要和附件元数据；查看原始数据或附件必须显式选择原因并形成 Break-glass 审计。
29. 作为管理员，我能看到销售授权范围及 CRM 映射异常；销售授权由后台授权目录决定，企业组织成员资格不等于录入权限。
30. 作为运维人员，若生产智能表格缺少核心字段、字段类型/枚举不匹配或关键权限不符合要求，服务就绪检查必须失败并明确显示原因，代码不得偷偷修改表结构。
31. 作为运维人员，媒体 MIME、真实内容格式、大小与校验和不符合安全基线时，系统应拒绝其进入 OCR/ASR/LLM 链路，保存失败与安全审计，并让后续消息继续。
32. 作为安全人员，生产媒体必须在私有对象存储中按不透明键保存，原始访问使用短时签名 URL 并先完成 Break-glass 审计；日志中不得出现媒体内容、下载 URL、访问凭据或完整敏感信息。
33. 作为审计人员，我需要追溯消息接收、AI 调用、字段来源、人工修改/确认、归属重分配、表格同步、CRM 调用、重试、废弃和原始数据访问；审计事件至少保留 180 天。
34. 作为系统，重复接收消息、连接重连、Worker 重试或管理员重试时，必须分别以消息、CRM 最终快照和通知类型保证幂等，避免重复建线索、重复更新和重复提示。
35. 作为系统，在 CRM 创建已经 `processing` 时收到废弃请求，必须等待 CRM 最终事实：CRM 成功则线索为 `synced` 且记录废弃未生效；CRM 失败才可保持废弃，不自动调用 CRM 删除补偿。
36. 作为系统，一条消息处理失败只是 Message Failure，不是 Conversation Failure；同一销售后续消息仍能继续处理。

## Implementation Decisions

### Architecture and runtime

- 使用 Python 3.12+、FastAPI、Pydantic v2、SQLAlchemy 2、Alembic、PostgreSQL、Redis、Celery、pytest、httpx、Jinja2；首期以模块化单体交付。
- 以 Docker Compose 作为开发、测试、PoC 和部署默认入口，至少包含 `app`、`worker`、`scheduler`、`postgres`、`redis`。时区为 `Asia/Shanghai`，PostgreSQL 使用持久化 Volume，容器日志输出到 stdout/stderr。
- FastAPI 不承担公网回调接入；它只提供健康检查、内部接口和 Operations Console。企业微信机器人使用 AI Bot SDK 长连接，且以接入 Adapter 隔离具体连接模式。
- 所有函数、方法和类方法必须有中文 Docstring；所有非平凡业务逻辑、分支、外部调用、数据转换与异常处理必须有中文注释。

### Reliability, ordering and task model

- 原始企业微信消息、其标准化结果与待处理 Outbox Event 必须在同一数据库事务中持久化；外部调用只由 Outbox 消费后的 Worker 发起。
- `message_id` 是消息接收幂等键。同一销售按数据库接收时间和持久化 `sequence` 串行消费；不同销售可并发。
- Lead Lifecycle State 与 Task Execution State 完全分离。业务状态为 `temporary`、`pending_create`、`synced`、`pending_update`、`company_identity_change_pending_review`、`merged`、`discarded`；任务状态为 `pending`、`processing`、`succeeded`、`retrying`、`failed_pending_review`。`company_identity_change_pending_review` 表示已同步记录的标准公司名称与最后成功 CRM 快照不一致，等待管理员依据 CRM 真实规则判定处理路径，不是任务失败状态。
- 可重试错误与不可重试错误必须分类。各 Adapter 使用独立配置的重试策略；CRM 自动重试上限为 3。达到上限后保留原始任务、错误摘要、次数和最后失败时间，供控制台人工处理。
- 首次处理失败并进入 `failed_pending_review` 后视为已越过该销售的顺序检查点；后续消息继续。失败消息的后续重试生成新的 LeadPatch，并依据当前状态、字段来源、冲突与人工编辑保护安全补充。

### Identity and ownership vocabulary

- `SalesIdentityProvider` 在消息进入任何线索/AI 流程前判断销售是否授权。数据库销售授权目录是运行时权威来源；环境变量仅允许用于启动、开发或紧急引导。组织目录同步未来仅用于补充资料，不能直接授予录入权限。
- 企业微信销售身份与 CRM 用户映射独立。`CRMUserMapper` 缺失时，禁止调用 CRM，创建不可重试的映射缺失同步结果，线索保持待同步。
- 禁止使用含义模糊的 `owner_id`。必须区分：
  - `original_capturing_sales_user_id`：最初采集人，不可因转交改变；
  - `smart_table_owner_user_id`：当前智能表格维护人和记录权限依据，可由管理员转交；
  - `submitting_sales_user_id`：单次 CRM Sync Record 的提交人；
  - `crm_lead_owner_user_id`：CRM 全局线索负责人，由 CRM 返回或其既有规则决定。
- Submission Ownership 不等于 CRM Lead Ownership；Smart Table Ownership 也不等于二者。所有转交、提交和 CRM 结果都必须保持该语义分离。

### Lead resolution, company and Smart Table

- Lead Resolver 按显式信号、引用关系、强身份、30 分钟当前上下文、近期历史、AI 语义依次归属；仍不可靠则为 `UNASSIGNED`。当前上下文只作辅助，过期的弱身份消息不得强行归属。
- 一条消息可拆出多条 Lead。无法可靠归属的附件仅是 Message Attachment，不自动成为任何 Lead Attachment，也不得复制给全部线索。
- Company Region Resolver 只在有明确国外证据时判为 `foreign`；`domestic` 使用企查查，`unknown` 可尝试企查查但失败不等于国外。
- 智能表格阶段唯一去重作用域为 `sales_user_id + standard_company_name`。同一销售内部遵循保守 Smart Table Merge：仅补空值；已有不同非空值保留冲突/补充信息，绝不静默覆盖人工值。
- CRM 提交阶段才按公司名称全局去重。CRM Duplicate Update 由 CRM Adapter 忠实适配企业 CRM 的现有行为；新提交空值通常不清空已有值，负责人保持 CRM 首次创建者，备注遵循 CRM 自身追加/更新规则。
- 临时线索允许无公司名称并保持 `temporary / incomplete_company`；不得提交 CRM。公司名称获得后仅与当前销售记录去重。已同步记录的公司/线索名称变更属于 `company_identity_change_pending_review`，不得自动作为普通 CRM Update；管理员须按 CRM 真实规则决定更名、纠错、新建或合并。
- 智能表格是共享的销售审核工作区，不是 CRM 全局主数据副本。机器人创建记录时必须写当前销售为负责人；普通销售对负责人和创建人只读，不能直接新建或物理删除记录。
- 已验证 PoC：关闭普通销售在智能表格中的“新增记录”权限后，机器人仍可以新增记录。该能力允许销售侧关闭直接新增入口，而机器人继续作为唯一的正常新增路径；该事实不替代后续对真实 CLI/API 契约的确认。
- 启动时执行 Smart Table Schema/Permission Check：按字段名校验核心字段、类型、枚举、人员格式与可验证权限。生产环境缺失 `AI待确认` 或其他核心结构时 readiness 失败；不自动创建或修改管理员维护的表。
- `WecomCliSmartTableAdapter` 是首期真实实现，只能在 Worker 中封装 `wecom-cli`。业务层只调用稳定表格接口；必须同时提供 Mock，实现可替换的未来 API Adapter。
- 每次 AI 写入前、CRM 提交前或管理员最终提交前重读表格。若当前值与 `last_ai_synced_value` 不同，则记录 `user_modified/user_confirmed`，移除相应 `AI待确认`，并永久禁止 AI 静默覆盖；首期不监听实时编辑事件。

### AI, media and data protection

- 定义 `LLMProvider`、`OCRProvider`、`ASRProvider`。首期默认实现分别使用 Qwen `qwen3.7-flash`、`qwen3.5-ocr`、`qwen3-asr-flash`，同时提供 Mock 实现。供应商、模型名、Base URL、API Key、超时和重试均由环境变量配置。
- 所有模型调用经 AI Gateway：统一 trace、超时、重试、错误归一化、调用量统计、脱敏日志和敏感数据处理扩展点。模型只理解/建议，不能决定提交授权、负责人、删除、CRM 合并或覆盖。
- LLM 输出固定执行 Parse → Schema Validation → Business Validation。仅对超时/截断/JSON 解析/结构错误允许一次结构修复；修复仅能修复结构，不能补造事实。业务规则或枚举/格式失败不得再次让 LLM “修复”。
- 置信度阈值配置化：高置信度（默认 `>=0.85`）经确定性校验后可填；中置信度（默认 `0.60–0.84`）可预填合法候选并写入 `AI待确认`；低置信度不写正式字段，仅存后台候选。
- `AI待确认` 是智能表格必需的多选审核元数据字段，不进入 CRM Payload，由系统维护。若 CRM 必填字段仍在其中，确定性提交命令必须发起一次显式机器人确认；卡片不可靠时使用不预填该必填中置信度字段的降级流程。
- 发送模型的数据遵循最小化原则：剔除或遮蔽身份证、银行卡、密码、验证码等无关高度敏感信息；手机号、邮箱和联系人仅在该字段提取确有必要时发送。OCR/ASR 只接收当前媒体，备注生成优先使用结构化字段和 enrichment。日志不得记录完整原始对话、完整联系方式、完整附件或密钥。
- Binary Artifact 内容不存 PostgreSQL；数据库只保留关联、MIME、名称、大小、SHA-256、存储键、处理状态和保留信息。`StorageProvider` 在开发/测试使用 Docker Volume，在生产使用私有对象存储。
- MediaValidator 在媒体进入持久化处理、OCR、ASR 或 LLM 前进行 MIME 白名单、大小上限、实际格式一致性与 SHA-256 检查。验证失败保留原始消息、写任务/安全审计、通知销售且不阻塞后续消息。
- 定义 `FileScanProvider`；首期可用 `NoopFileScanProvider` 与 `not_required` 状态。启用真实扫描后只有 `clean` 媒体可进入后续 AI 或 CRM 附件链路。
- 生产对象存储必须私有、服务端加密、最小权限、按环境隔离，使用无 PII 的不透明存储键；短时签名 URL 仅在 Break-glass 审计后生成，禁止写日志。未满足此基线不得标记生产就绪。

### Submission, CRM and notifications

- CRM 写操作仅能由 Deterministic Command Parser 识别的固定命令发起，并同时验证当前销售身份与权限；首期命令为“提交今天的线索”“提交我的更新”。
- `pending_create` 项目级最小必填为公司/线索名称、业务线、手机号/电话/邮箱至少一种。CRM Adapter 仍要执行 CRM 接口自身硬性校验，且其实际要求优先。
- 提交前必须重新读取智能表格，构造 Final Snapshot 与规范化 CRM Payload，处理人工编辑、公司状态、枚举、格式、地点和必填校验。批量提交始终部分成功。
- “提交我的更新”仅分页读取当前 Smart Table Owner 的已同步记录。由统一 Payload Builder 规范化并比较当前 CRM Payload 与 Last Successful CRM Snapshot；AI待确认、内部状态、置信度、字段排序及标准化后等价的空值不构成更新。
- CRM 幂等键为 `hash(smart_table_record_id + canonical_snapshot_hash + operation_type)`。同记录、同规范快照和同操作类型必须复用此前成功结果，不再次调用 CRM；有效字段变化产生新的快照与合法更新。
- CRM Sync Record 至少保存幂等键、表格记录、操作、快照哈希、CRM lead ID、提交销售、CRM 负责人（可取得时）、状态、尝试次数、响应摘要、创建与完成时间。
- CRM 成功只更新后端同步元数据，绝不将 CRM 业务字段或 CRM 负责人回写/覆盖智能表格；因此跨销售去重不得破坏智能表格权限。
- 未开始的 CRM Create 在废弃后必须取消或跳过。CRM 已在处理时的废弃遵循外部事实优先：成功即 `synced`，记录 `discard_request_not_effective`；失败可保持 `discarded`；禁止自动 CRM 删除补偿。
- 机器人通知以 `hash(sales_user_id + source_message_id + notification_type)` 幂等。相同类型默认只发送一次；真实状态变化使用新通知类型。Notification Record 保存状态、发送时间、提供器消息 ID 与尝试次数。

### Operations, audit and retention

- Operations Console 位于受限测试/内网环境，开发可使用显式 Development Auth，并通过 `AdminIdentityProvider` 隔离认证。生产不得匿名访问，生产身份基础设施未确认前不绑定某个 SSO/OAuth 方案。
- Console 默认脱敏显示。查看原始消息、完整联系方式、预览或下载附件均为 Break-glass 操作，必须记录操作人、角色、对象、访问类型、原因、时间及可用的请求上下文；禁止批量导出全部原始聊天。
- 审计至少涵盖消息、AI、字段变更、表格新增/更新、人工编辑检测、确认、归属、CRM、重试、合并/去重、废弃、转交、管理员操作、原始数据访问与媒体安全。审计保留期配置默认不少于 180 天。
- Raw message、附件、OCR/ASR 结果和 AI 中间产物使用单独的环境变量保留期。Celery Beat 只触发清理任务，实际删除由 Worker 执行；媒体先删存储、成功后更新数据库状态，部分失败必须保留可重试审计，审计事件到期后才能删除。

## Testing Decisions

### Primary test seam

首期以“消息进入后的应用服务边界”为最高价值测试缝：给定已持久化消息、销售身份和可替换 Adapter，观察其产生的 Outbox、Lead/Field Provenance、智能表格增量、CRM Sync Record、审计与通知，而不是在测试中依赖真实企微、Qwen、企查查或 CRM。

该缝使用真实测试数据库事务验证“原始消息 + Outbox 同事务”与幂等；使用 Fake/Mock Adapter 验证外部行为。Worker 侧以可单独执行的 Outbox/任务消费者测试排序、重试、失败越过和补充重试。此设计使核心业务规则可在没有外部接口资料时被完整验证。

### Required behavior coverage

- 消息 `message_id` 重复、同销售有序/跨销售并发、失败消息不阻塞后续消息。
- 未授权销售零副作用；已授权但 CRM 映射缺失可采集不可提交。
- 多客户拆分、弱身份超时进入待归属、受权限限制的人工重归属与安全 provenance 回算。
- 同销售公司去重、跨销售智能表格隔离、临时线索升级、企查查失败/人工确认、公司身份变更人工审查。
- Smart Table Merge 的保守规则、人工编辑保护、`AI待确认` 移除、必填中置信度字段的阻塞确认和卡片降级。
- Smart Table schema/readiness 校验，以及转交后只变更 Smart Table Owner 并验证表格权限。
- Final Snapshot 规范化、`pending_update` 差异发现、CRM 幂等、批量部分成功、CRM 重试分类与 CRM 返回不回写表格。
- 废弃与 CRM `processing` 的竞态，以及已同步线索不得从本系统废弃 CRM。
- 媒体 MIME/大小/真实格式/checksum、扫描状态、附件归属、ASR 失败反馈和媒体存储安全策略。
- AI Gateway 最小化和脱敏日志、结构修复至多一次、业务校验不触发模型“修复”。
- 通知幂等、Break-glass 审计、保留期清理的成功/部分失败重试语义。

### Integration and acceptance testing

- Docker Compose 环境必须覆盖 `app`、`worker`、`scheduler`、PostgreSQL 与 Redis 的启动、健康检查和日志可见性。
- 首个真实验收环境仅验证企业微信机器人长连接、授权销售身份、Qwen 调用和 `wecom-cli` 智能表格增量写入及记录权限；企查查和 CRM 使用明确标注的 Mock Adapter。
- 真实 CRM、企查查、对象存储、扫描、地图和生产认证的集成测试，必须在相应接口契约和测试凭据到位后追加；不得依据猜测构造“真实”调用。

## Out of Scope

- CRM 内部商机跟进、合同、销售预测和 BI 报表体系。
- 微服务拆分、复杂 Workflow Engine、多渠道机器人、每名销售独立智能表格。
- 公网 HTTPS 回调模式、智能表格实时编辑事件、语音自动切片/分段 ASR/自动修复超长音频。
- 自行引入具体恶意文件扫描引擎、实时跨销售智能表格去重、CRM 负责人自动转交、CRM 自动删除或补偿删除。
- 通过自然语言或 LLM 解释提交、废弃、归属、合并或负责人变更意图。
- 生产身份系统的具体选型、未获合同确认的 CRM/企查查接口行为、未经验证的智能表格卡片/API 能力。

## Further Notes

### External implementation dependencies

以下资料缺失时只能记录为依赖，不能由实现自行猜测：

1. 企业微信 AI 机器人 SDK 的实际连接配置、消息格式、身份字段、重连语义、消息回复与卡片确认能力。
2. 智能表格能力状态：已验证普通销售关闭“新增记录”权限后，机器人仍可新增记录。仍待确认的 CLI/API 契约包括目标表的 `doc_id`、`sheet_id`、字段/枚举/人员格式和记录级权限配置，以及 `wecom-cli` 的认证、命令参数、返回结构、错误码、分页、超时、重试和权限读取能力。
3. 企业 CRM 的 API 契约：认证、用户映射、字段映射和硬性校验、公司查重、创建/更新/备注、负责人保持、重命名/纠错/合并与幂等行为。
4. 企查查 API 的认证、查询参数、唯一匹配判据、候选结构、企业标识和限流/错误语义。
5. 生产对象存储、文件扫描、地图/逆地理编码和企业身份系统的产品选型、接口、安全策略与测试凭据。
6. 各环境具体的 MIME 白名单、文件大小、保留期、重试次数、推送阈值、上下文时长和签名 URL 有效期配置值。
