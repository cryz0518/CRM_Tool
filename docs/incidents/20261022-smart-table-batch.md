# 2026-10-22 智能表格首次录入与网络故障

## 已确认的原因

- 自由文本的 AI 路径在首次入表后才执行公司核验，造成简称先入表、随后逐行改名；显式标签路径的执行顺序与之不一致。
- 批量写入被可选文本列“系统线索ID”限制；生产表没有此列时静默退回单行新增。
- 不足一批时按每条记录自己的等待时间过滤，连续消息会分别到期、分别写入。
- 解析结果在外部写入成功前只保存在批次载荷中，后台草稿尚未填充。巴可消息的批次载荷已有完整公司名，网络失败后草稿为空不代表解析未提取公司。
- `893101` 的只读复现返回 `NetworkError`，底层原因为 `kind=connect; client error (Connect); tls handshake eof (io: Other)`。这是 TLS 建连阶段中断，不能据此判断表格限流或字段非法；尚未确定链路上由哪一端关闭连接。
- 临时草稿升级后，旧字段来源中的简称可能再次覆盖已标准化公司名；已 ACK 的新增记录在后续失败时也必须保留远端标识。

## 修复后的行为

1. 消息解析、天眼查公司核验和销售内去重在首次入队前完成；安全字段、补充素材和来源先持久化。
2. 默认积累 5 条就绪线索，或最早就绪记录等待 60 秒后，批量写入当前已就绪的至多 5 条；触发时间受 Scheduler 轮询间隔影响。
3. 首次新增包括核验后的公司名、业务字段与固定模板备注；没有系统列时按公司名批量查找并校验负责人，不再降级为逐行新增。
4. 网络失败后先回查未知结果；已获 ACK 的记录保留标识，后续只恢复原行。重试复用持久化补丁，不重复消耗模型和天眼查调用。
5. 批量成功建立的字段基线与旧候选同时更新，继续保留 T09 人工编辑保护、消息顺序、字段来源和通知规则。

## 回归边界

- 三条自由文本：先完成三次工商查询，等待期间表格为空；只有最早一条到期也一次新增三条，后续无逐行更新。
- 无系统列的网络失败：覆盖请求未落地、请求落地但响应丢失两种情形；保留公司名，恢复后只有一行。
- 继续覆盖临时草稿升级、国外公司显示名、同一线索多条补充、ACK 后核验失败和人工修改保护。
- TLS 握手中断仍可能再次发生；本次修复确保应用保存事实并安全恢复，不宣称外部网络已永久修复。
