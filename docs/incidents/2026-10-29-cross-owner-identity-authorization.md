# 跨员工 CRM 提交授权未识别：回调身份与通讯录身份未统一

## 现象和根因

2026-10-29，已获跨员工提交授权的成员发送指定负责人、指定日期的提交指令，
机器人仍提示“当前账号没有跨员工 CRM 提交授权”。请求在候选查询前被拒绝。

授权命令通过通讯录确认成员，把专用权限保存到通讯录成员对应的 Actor Registry 行。
新机器人的消息回调使用另一种发送者标识，接入模块按真实发送者创建独立记录。
人员字段写表流程已经能够核验两者对应关系，但提交权限检查仍直接读取回调记录，
没有复用该映射，因此错误地认为未获权。只读通讯录查询确认两种身份唯一对应同一成员，
原有权限没有被入站消息覆盖。

## 修正范围

- `app/crm/authorization.py` 集中读取跨员工专用权限。先检查原始发送者是否启用，
  再按真实发送者标识通过现有 Adapter 核验唯一通讯录成员，读取其当前授权。
- 指令入口、候选查询、卡片领域执行、冻结提交及最终持锁复核共用该判断。
- 直接持有专用权限的成员保留原行为；系统管理员标记本身不能替代专用授权。
- 不按姓名继承权限，不向回调记录复制权限，不缓存授权布尔值。
  任一身份停用或原授权撤销都能阻止后续提交，身份映射仍复用 Adapter 缓存。
- 最终持锁复核同时锁定通讯录授权行；消息、卡片及 CRM 审计保留原始操作者身份。
- 不新增数据库表或迁移，不改变一次候选查询、卡片快照复用及成功状态批量回写。

## 验证记录

新增 `tests/unit/test_crm_submission.py` 中的 `split_identity` 回归用例，
在 Docker 隔离网络、SQLite 和 Mock 外部适配器环境中执行：

```bash
docker compose run --rm --no-deps app pytest \
  tests/unit/test_crm_submission.py -k split_identity -q
```

测试容器必须包含当前源码；上面是构建当前测试镜像后的运行命令。
测试夹具隔离真实 `.env` 和员工目录，不发起真实 CRM 请求。

| 场景 | 结果 |
| --- | --- |
| 通讯录授权身份与无姓名回调身份不同，指令发卡及卡片领域执行 | 通过；仍只查询一次表格，提交审计保留回调身份 |
| 候选产生后撤销通讯录成员专用权限 | 拒绝 CRM 调用 |
| 候选产生后停用通讯录成员 | 拒绝 CRM 调用 |
| 候选产生后停用原始回调身份 | 拒绝 CRM 调用 |
| 显示名相同但映射到另一个成员 | 拒绝 CRM 调用 |
| 通讯录映射发生异常 | 拒绝 CRM 调用，仅记录异常类型 |
| 生成 CRM 载荷后、最终持锁复核前撤销授权 | 拒绝 CRM 调用，未创建同步记录 |

新增 7 项全部通过。另对 CRM 提交、企微动作、CLI 智能表格、消息接入四个测试文件的
338 项既有测试进行修改前后对照：均为 306 项通过、32 项相同既有失败，无新增失败。
历史失败含已取消的独立查重/重复确认断言及过时夹具，本次未修改这些业务语义。
Ruff 和 Git 空白检查通过。本次不宣称全仓回归全部通过。

服务器另以这条真实指令做独立诊断进程内的只读对照：原权限入口返回拒绝，
在该进程内载入修复函数后，成功解析“范春娜”的唯一负责人范围。
该验证未覆盖服务器源码文件，未修改权限记录，未发行卡片或调用 CRM，
不代表常驻 Worker 已经完成版本更新。

## 发布与运维

修复必须随应用镜像发布到目标环境后才能改变常驻服务行为；仅保存本地文件不会修复服务器。
无需重新授予成员权限，也不应通过按姓名批量复制权限来绕过问题。
发布后先只读检查原授权是否能用于真实回调，再由销售重新发起提交指令并勾选候选卡。
旧拒绝通知是历史处理事实，不自动重放成 CRM 提交。
