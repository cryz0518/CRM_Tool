# SQL 查询把富文本备注缩成链接片段，导致 CRM 待完善误报

## 现象与证据

广东西朗德光学科技有限公司的备注有完整内容，提交却显示“待完善”。
2026-10-30 08:38:17 的审计事件为 `crm_create_payload_invalid`，尚未调用 CRM。

对同一条表格记录做只读对照发现：

- 直接 SQL 选择备注时，返回一个 `{text, type, url}` 对象；`text` 只有备注内的网址，
  长度 19，不能代表备注全文。
- 原生记录列表返回多个富文本片段，按顺序拼接后可以通过原有备注长度校验。
- 旧解析器直接提取链接对象的 `text`，把局部网址当成完整备注，再送入 CRM 载荷校验。
- 后台旧草稿与表格全文的读取口径不同，不能用后台旧值掩盖表格查询丢失内容的问题。

因此问题是读取链路丢失富文本内容，不是要求销售为已有备注补字。

## 修复

`WecomCliSmartTableAdapter._build_query_sql()` 对 TEXT、LONG_TEXT 字段统一使用
`REPLACE(字段, "\n", "\n") AS 原字段名`，让公式引擎将单元格内容投影为完整文本。
搜索和替换使用相同内容，不改变换行、网址、邮箱或其它正文。
该投影已在生产同一条记录上与原生接口全文逐字对照。

SQL 公式引擎不支持 CONCAT，因此不能用字符串拼接强制转文本。
当前做法不新增 CLI 请求，也不引入逐行补读、后台旧值兜底或新的缓存。
负责人、日期、状态过滤与日期格式化继续在同一条 SQL 中执行。

`_parse_query_record()` 不再接受文本字段中的单个链接对象作为全文；
若服务端未按投影契约返回完整字符串，则按协议错误终止，避免静默丢失内容。
备注的 30–1000 字符校验保持原规则。

## 验证

- 适配器整文件 114 项通过。新增用例覆盖 TEXT/LONG_TEXT、单条/批量/负责人查询、
  网址与邮箱、多行与 CRLF、Unicode、JSON 外观文本和空值，验证记录查询仍只有一次。
- 新增提交链路用例验证：真实 CLI 适配器读取全文后写入卡片候选快照；
  回调只复用该快照，之后表格变化不影响已冻结载荷，也不触发候选回读。
- 生产独立诊断进程只读复现：修复前得到 19 字符链接片段；修复后全文与原生接口一致，
  一次记录查询即可通过最终载荷校验。未发行卡片、修改表格或调用 CRM。
- 四个相关测试文件的 344 项未变更契约用例在修改前后均为 312 通过、32 项相同既有失败，
  没有新增失败。历史独立查重/重复确认断言及过时夹具不在本次修复范围。

## 发布与恢复

无需数据库迁移，无需修改或覆盖销售备注。
发布使用本地构建镜像传到服务器加载，保留服务器 `.env` 和 `Dockerfile`。
发布后只读核对真实记录的完整备注、CRM 载荷校验和跨员工权限，
然后由销售重新发起提交并确认候选卡。历史失败动作不自动重放成真实 CRM 请求。
