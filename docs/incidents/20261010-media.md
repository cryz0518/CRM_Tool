## 实际根因

图片 08:42:35 已保存，扫描器是 `noop`，故扫描结果为 `not_required`；OCR 队列和处理入口却只接受 `clean`。附件长期 pending，同销售随后消息因顺序检查等待它。

语音 08:59:18 的官方帧已经提供 `body.voice.content`，长度 32，没有音频下载地址。接入层旧实现忽略转写、统一要求媒体下载，因而错误登记 `media_download_failed`。该消息随后也被前面的图片阻塞。

当前安装 Python SDK 为 1.0.2，回调透传原始字典；官方 Node 协议的 VoiceContent 定义 `content: string`。本次核对了[官方语音协议类型](https://github.com/WecomTeam/aibot-node-sdk/blob/master/src/types/message.ts)及[官方 Python 类型定义](https://github.com/WecomTeam/wecom-aibot-python-sdk/blob/master/aibot/types.py)。

## 修复与安全语义

`not_required` 表示**没有执行扫描**，并非安全扫描通过。只有组装层确认非 production 环境且明确选择 `MEDIA_SCANNER_PROVIDER=noop`，才授予扫描豁免处理资格；直接构造媒体服务默认不允许豁免。现有 production 策略继续拒绝 noop/fake，真实生产扫描 Adapter 尚未安装，不能把该状态改成 clean 来绕过策略。

感染、隔离、扫描失败、超时及不允许的豁免都进入可观察失败终态；实际 MIME、大小和冻结摘要在存储读取后再次校验。下载、扫描、上传及识别失联等待使用已有 `LEAD_PROCESSING_TIMEOUT_SECONDS` 配置，过期后转 `failed_pending_review`，释放同销售顺序检查点。迟到上传只完成存储事实，不能重新打开已失败媒体任务；经受控重新扫描通过后可恢复媒体识别，但不会自动重放已越过的消息检查点。

可信、非空 `voice.content` 在接入层写入同一个来源消息，直接进入既有文字处理流程；同时有音频时也只使用这一份正文，不下载和重复提取。仅有音频下载地址时沿用原下载、扫描和 ASR 流程。消息 ID 排重、既有销售身份校验、sequence、原帧及引用证据保留。

## PR #90 复审修正：重新扫描计时与状态

扫描等待使用本轮 scan_started_at；尚未开始扫描的历史队列才回退到 created_at。上传等待独立使用冻结上传 intent 的 remote_started_at/created_at。识别阶段以任务登记和本轮 scan_completed_at 中较晚的时间为阶段边界，外部 OCR/ASR 调用仍执行现有 provider 超时；不以附件数日前的创建时间立即判定新扫描或识别超时。本次复用现有字段，无 schema 迁移。

显式进入 scanning 时，未完成的附件和识别任务同步为等待状态并清除旧完成标记；未完成上传仍等待上传，已成功识别的附件不会再次识别。感染/隔离、扫描失败及实际超时仍形成失败终态。扫描超时记为 scan_failed；迟到 clean 不自动重开，未经过轮询的迟到成功回调也会检查本轮期限。恢复需要新的显式扫描，不能靠迟到回调越过终态。

新增回归覆盖数日前附件、多次扫描轮询、扫描成功/失败/超时、轮询前后迟到回调、上传与识别的独立时间边界。尚在有效扫描期限内的来源保持 pending，同销售后续消息等待；已结束的来源 Outbox 始终保留原终态，媒体恢复不自动重放。隔离 PostgreSQL 验证新扫描等待不会提前释放顺序检查点。
